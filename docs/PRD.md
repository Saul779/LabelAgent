# 1. 项目概述

## 1.1 背景

“在场”APP 当前主要存在以下问题：

1. 任务主要依赖首页曝光，匹配比例低、撮合时间长。
2. 商品、任务和动态内容缺少稳定的分类、标签语义，难以支持筛选和个性化推荐。
3. 用户画像、职业认证、技能认证和行为数据尚未形成统一的推荐输入。

## 1.2 产品目标

- 面向“在场”APP 全体用户建设个性化推荐能力。
- 对动态内容生成可用于筛选和召回的分类、标签、置信度和证据。
- 建设用户画像、技能标签库及标签相似度能力。
- 将用户画像与商品、任务、动态标签进行匹配。
- 对符合条件的用户发送任务邀请或消息提醒。
- 业务目标：将成交任务平均成交时间缩短至 **30 分钟以内**。

## 1.3 当前需求成熟度

原始《推荐系统-产品文档》曾将多项能力标记为“暂未规划开发”；2026-08-19 已补充确认 **S4 商品打标** 的产品与技术口径。其他能力仍按各自状态跟踪。因此：

- 本文可以定义目标行为和建议架构；
- 不代表相关能力已经排期；
- 版本、负责人、日期和验收计划仍需产品确认。

# 3. 动态内容分类与标签

## 3.1 输入

Agent 接收以下动态内容：

- 文字；
- 图片；
- 视频；
- 文字、图片、视频的混合内容。

当前需求没有把“独立音频”定义为输入类型。视频音轨是否必须执行 ASR，随视频方案一起确认。

## 3.2 模型行为

- Agent 角色为“专业内容理解助手”。
- 基线要求采用非思考模式直接输出，以满足即时性目标。
- 是否固定使用非思考模型、具体延迟和重复运行一致率仍需压测后确认。
- 输出必须是严格 JSON，禁止附加解释文本。

## 3.3 分类规则

1. 分类围绕电商、任务、日常三类内容场景设计。
2. 分类必须唯一、不重叠、相互独立。
3. 每条动态要求一个一级分类和一个二级分类。
4. Agent 只能从给定分类库选择，不得创建分类。
5. 最高有效置信度低于 `0.50` 时：
   - 一级分类输出“未分类”；
   - 分类置信度输出 `0.00`；
   - 二级分类为空。
6. “全部”仅作为列表筛选项，不作为 Agent 可输出分类。

当前一级分类基线包括：校园生活、摄影、萌宠、健身、艺术、穿搭、科技数码、家居、户外、美食、未分类。

> 冲突：需求要求输出二级分类，但基线中的二级分类表为空。二级分类字典冻结前，建议允许 `secondary_category=null`，不得由 Agent 自创二级分类。

## 3.4 标签规则

1. 标签采用面向电商、任务、日常场景的扁平结构。
2. Agent 优先从给定标签库复用标签；检索标准标签、别名和近义项后仍无合适标签时，允许创建新的标准标签。
3. 输出 **0～5 个**标签：
   - 仅保留最终置信度 `>=0.50` 的标签；
   - 按最终置信度降序排列；
   - 最多保留前 5 个；
   - 无有效匹配时返回空数组 `[]`。
4. Agent 输出标签必须真实写入动态，供标签合集页和推荐召回使用。
5. 新标签创建成功并取得稳定 `tag_id` 后，可用于当前打标结果；结果需标记来源为 `created`。
6. 标准标签与别名的输出口径尚未确认；确认前建议统一写标准标签，别名仅用于匹配。

### 用户手工标签

- 普通用户可以手工添加标签。
- 未匹配到标准标签库的手工标签进入“未分组”。
- 手工标签与 AI 标签必须记录不同来源。
- 建议合并时按标准标签 ID 去重；手工标签是否覆盖、补充或独立展示，待产品确认。

## 3.5 分类与标签库

当前规则明确区分：

- **分类库**：Agent 只读匹配，不允许创建分类；
- **标签库**：Agent 优先复用，查重无可复用项后允许创建新标准标签。

最低需要：

- 一级/二级分类字典；
- 标签名称和可选别名；
- 启用状态；
- 版本；
- 内容场景或标签分组；
- 标准标签、别名和近义项联合查询；
- 归一化名称唯一约束、幂等键和原子创建；
- 稳定 `tag_id` 分配；
- 创建来源、证据、模型和 Prompt 审计；
- 标签新增、改名、停用、合并及变更事件。

Agent 只能通过标签治理接口创建标签，不得绕过治理接口直接写标签库。自动创建的最低置信度、是否立即启用以及低置信度是否先进入人工审核，仍需产品确认。

## 3.6 置信度与证据

### 基础要求

- 分类和每个标签均输出 `0.00～1.00` 的置信度，保留两位小数。
- `0.80～1.00`：存在直接、明确证据。
- `0.60～0.79`：存在部分线索，需要合理推理。
- `0.50～0.59`：弱关联、边缘元素或较长推理链。
- `<0.50`：无效匹配。
- 证据必须引用具体文字、画面或可验证行为。
- 分类证据和标签证据分别输出，证据强度应与置信度一致。

### 规则引擎

规则引擎属于当前需求基线，不是仅预留的未来能力。它至少校验：

1. 证据真实性；
2. 分类/标签与证据的自洽性；
3. JSON 格式、标签在库状态和分数范围等输出稳定性。

最终置信度按基线公式计算：

```text
Final_Conf =
  LLM 自评分
  × min(证据真实性系数, 标签自洽性系数, 输出稳定性系数)
```

- 输出阈值以规则引擎修正后的 `Final_Conf` 为准。
- 完全无法解析时丢弃候选结果，分类回退“未分类”且置信度为 `0.00`，标签返回 `[]`。
- 证据真实性区间在 80% 处存在重叠；建议统一为 `>=80%` 与 `50%～<80%`。
- 各系数具体取值、自动修复策略和人工审核阈值仍需产品冻结。

## 3.7 输出 Schema

```json
{
  "primary_category": {
    "name": "摄影",
    "confidence": 0.92,
    "evidence": "画面主体为相机和拍摄场景"
  },
  "secondary_category": null,
  "tags": [
    {
      "name": "原创",
      "confidence": 0.86,
      "evidence": "正文明确说明为本人拍摄"
    }
  ]
}
```

约束：

- `primary_category` 必填；
- 二级分类字典未冻结时，`secondary_category` 可为 `null`；
- `tags` 必须为数组，可为空；
- 置信度是规则引擎修正后的最终置信度；
- 示例中的字段名是本 PRD 的规范化建议，需在接口评审时冻结。

# 4. 任务分类与接单路由

## 4.1 需求流程

任务处理包含两个相互独立的维度：

```text
维度一：接单方式
├─ 指定人接单
│  ├─ 历史任务曾指定该接单人
│  │  └─ 查询数据库并返回该接单人的 userID
│  └─ 历史任务未指定该接单人
│     └─ 仅返回当前指定的接单人名称
└─ 公开接单
   └─ 不处理指定接单人

维度二：任务类型（所有任务均执行）
├─ 关系类
│  └─ 提取重点：寻找某个人 / 寻找其他事物
├─ 技能类
│  └─ 提取重点：需要的技能 + 线下/非线下
└─ 甜品类
   └─ 提取重点：线下/非线下
```

任务类型分支不是标签或 S3 内容分类。T1 Agent 根据任务描述与图片在关系类、技能类、兜底类中判断一个业务分支，再提取该分支的重点信息。

## 4.2 后端确定性规则

以下能力必须由业务后端根据结构化字段和权威数据库处理，不得由 Agent 猜测：

- 根据 `accept_mode` 区分指定人接单与公开接单；
- `accept_mode` 正式且仅允许 `public/specified`；缺失、空值或其他取值必须在调用 Agent 模型前拒绝；
- 指定人接单不限制指定对象；
- 查询当前任务发布人以前发布的任务；
- 判断历史任务中是否曾经指定过当前接单人；
- 若曾指定，查询数据库并返回该接单人的 `userID`；
- 若未曾指定，仅返回当前接单人名称，不追加候选用户或强制绑定 `userID`；
- 接单权限、用户状态、黑名单及订单状态校验；
- 保存路由结果和执行实际派单。

业务后端不再要求预先提供任务类型。T1 Agent 必须根据任务内容自行判断关系类、技能类或兜底类；结构化输出字段正式使用 `biz_task_type`，schema 1.0 固定取值为 `relationship/skill/dessert`。

## 4.3 Agent 语义能力

Agent 不判断任务属于哪一种类型，而是根据业务传入的 `task_type` 提取对应重点信息：

- 关系类：提取目标是“某个人”还是“其他事物”，以及具体目标描述；
- 技能类：提取需要的技能，并提取“线下”或“非线下”；
- 兜底类：非关系类、非技能类任务均进入该类，当前沿用编码 `dessert`，仅提取“线下”或“非线下”；
- 指定人名称由任务输入直接提供；Agent 不负责查询或猜测 `userID`。

该分支逻辑不复用 S3 动态内容的分类、标签数量和置信度规则。T1 只在三个固定分支中判断，不能创建新分支。

首版输入仅支持文本和图片。图片信息与描述或正文冲突时，以描述和正文为准。

## 4.4 建议输出结构

```json
{
  "accept_mode": "public",
  "task_type": "skill",
  "relation_target": null,
  "relation_target_detail": null,
  "required_skills": ["电脑维修"],
  "service_mode": "offline",
  "specified_assignee": null
}
```

指定人接单建议由后端补充：

```json
{
  "accept_mode": "specified",
  "specified_assignee": {
    "input_name": "张三",
    "historically_specified": true,
    "returned_user_id": "u_123",
    "returned_name": null
  }
}
```

若历史任务中未曾指定该接单人：

```json
{
  "specified_assignee": {
    "input_name": "张三",
    "historically_specified": false,
    "returned_user_id": null,
    "returned_name": "张三"
  }
}
```

`biz_task_type` 为正式字段名；`service_mode` 固定为 `offline/non_offline`。上门、到店、现场映射为 `offline`，线上、远程映射为 `non_offline`；两类方式同时明确出现时不强行二选一，返回空值并进入审核。分支编码随 TaskDetailResult schema 版本管理，不单独引入注册表版本。

# 6. 搜索、推荐与触达

本节来自架构参考，具体产品版本仍待确认。

## 6.1 搜索链路

建议链路：

1. Trie 前缀匹配生成搜索联想；
2. 分词、停用词过滤和关键词提取；
3. Redis 查询 Query/关键词到标签的缓存；
4. 未命中时生成 Query Embedding，在 Milvus `tag_vectors` 中检索相似标签；
5. ES 使用标签 ID `terms` 过滤并结合 BM25；
6. GBDT 精排、去重、多样性重排和缓存；
7. 纯数字、型号等精确查询直接走 ES。

Query Embedding 的负责系统、模型版本和降级策略待确认。建议由搜索中台提供轻量在线 Embedding，不调用 LLM。

## 6.2 用户浏览推荐

建议同时使用（用户侧数据由画像服务提供，不由本 Agent 生产）：

- 用户高权重标签：用于可解释规则和标签扩展；
- `user_vector`：用于在 `tag_vectors` 中召回相似兴趣标签。

合并标签后由 ES 召回内容，并进行：

- 类目、价格等业务过滤；
- 近期曝光过滤；
- GBDT 精排；
- MMR、多样性、新鲜度及业务规则重排；
- 推荐结果缓存。

## 6.3 内容反向匹配用户

新任务或动态发布后：

1. 内容完成标签化；
2. 基于内容标签形成查询向量；
3. 查询 `user_vectors`，返回相似用户 ID；
4. 过滤活跃度、频控和免打扰设置；
5. 交由触达系统发送消息提醒。

## 6.4 触达

产品基线只确认“任务消息提醒”方向。Push、站内信、短信、邮件的渠道范围、模板、频控、用户授权和撤回策略均待确认。

若使用生成式个性化文案，应采用离线预生成或明确作为异步例外；不得破坏“搜索与推荐在线链路不调用 LLM”的原则。

# 7. Agent 能力边界

| 场景代号 | 能力 | 需求状态 | Agent 输出 |
|----------|------|----------|------------|
| S1（建议编号） | 职业认证材料解析 | 待确认、未排期 | 规格待定 |
| S2（建议编号） | 技能认证材料解析 | 待确认、未排期 | 规格待定 |
| S3（建议编号） | 动态内容分类与标签 | 需求已定义、排期待确认 | 分类、0～5 标签、最终置信度、证据 |
| S4（已确认编号） | 商品分类与商品搜索词生成 | MVP 已实现；生产化待验收 | 唯一一级/二级路径或 unknown、置信度、审核原因、搜索词或候选分类建议 |
| T1（建议编号） | 自动三分支判断、任务信息提取与后端接单人查询 | 文本+图片 MVP 已实现；正式分支编码待冻结 | 人/事物目标、所需技能、线下/非线下；历史 userID 或当前名称由后端追加 |

S1～S3 是本文为便于架构讨论使用的建议编号；T1 用于映射任务分类需求图。**S4 已正式确认为商品打标场景**。用户画像语义打标仍不纳入本 Agent，且不再占用 S4 编号。

Agent 不负责：

- 搜索联想、在线 Query 理解和 ES 检索；
- Milvus 在线 ANN 执行；
- 推荐召回、排序、曝光过滤和频控；
- 消息实际发送；
- 用户行为采集和 Spark/Flink 聚合；
- 创建分类；
- 绕过标签治理接口直接修改标签库。

# 8. 数据与交互

## 8.1 核心数据

- `CategoryDictionary`：一级/二级分类字典及版本；
- `TagDictionary`：可选标签、别名、分组、状态及版本；
- `ContentLabelResult`：分类、标签、最终置信度、证据；
- `ProductLabelResult`：S4 商品一级/二级类目、最终置信度、审核原因、搜索词与候选分类建议；
- `TaskDetailResult`：接单模式、任务类型、关系目标、所需技能、线下/非线下及指定人查询结果；
- `TagVector`：标签语义向量；
- ES 内容文档中的标签 ID；
- Redis 中的 Query→标签、用户标签画像、频控和推荐缓存。

## 8.2 交互原则

- 业务服务通过 MQ 异步触发 Agent；
- MQ 消息携带业务 ID、类型和版本，Agent 按权限读取原始内容；
- Agent 发布打标结果事件；
- 搜索中台作为 ES 索引建议唯一写入方；
- Agent 通过 Milvus 代理写向量，不直接执行在线 ANN；
- 历史订单和用户身份由业务后端查询；Agent 不直接把自然语言姓名认定为 `userID`；
- 协议字段、幂等、重试、删除语义和部分成功状态在接口设计中冻结。

# 9. 审核、监控与验收

## 9.1 人工审核

- 低置信度或规则校验异常结果进入人工处理；
- 人工结果用于优化提示词、分类库、标签库和模型；
- 审核角色、队列 SLA、抽检比例、回滚和审计要求待确认。

## 9.2 建议验收指标

除“平均成交时间不超过 30 分钟”外，基线没有给出技术验收阈值。建议补充：

- 一级/二级分类准确率；
- 标签 Precision、Recall、F1；
- 关系目标、所需技能和线下/非线下提取准确率；
- 技能提取 Precision/Recall；
- 历史指定接单人 `userID` 查询正确率；
- 严格 JSON 合规率；
- 证据可验证率；
- 重复运行一致率；
- 文字、图片、视频及混合内容 P95 延迟；
- 单条 Token/模型成本；
- 人工审核率；
- 推荐 CTR、接单率、消息转化率；
- 任务成交时间 P50/P90。

这些指标需要金标测试集和正式阈值后才能验收。

# 12. S4 商品打标补充需求（已确认）

详细 Prompt 与实现规则见 [Agent-商品打标](./Agent-商品打标.md)，类目源见 [在场电商平台商品分类信息.xlsx](./在场电商平台商品分类信息.xlsx)。本节只冻结产品行为和验收口径。

## 12.1 输入与业务约束

- 商品标题非必填；图片允许 0～5 张，典型为 3～5 张；标题和图片至少提供一种；
- 不区分主图和详情图；图片采用 OCR + Vision；
- 标题和图片冲突时以标题为分类依据，但必须标记冲突并进入人工审核；
- 一个商品只允许一个一级分类和一个二级分类，当前不处理多主体和套装；
- 允许输出 `unknown/no_match`。

## 12.2 分类与置信度

- 从二级叶子类目执行混合召回，一级分类由二级类目的父级映射得到；
- 模型 A 选择二级类目或 unknown，模型 B 使用第二模型独立复核；
- `confidence` 对完整一级/二级路径合并计算，两模型一致时最终分数取二者较小值；
- 自动通过阈值为 `0.85`；模型不一致、任一模型 unknown、标题图片冲突或确定性规则失败时进入人工审核；
- 类目知识由 LLM 生成并直接使用，不经过运营审核，但必须通过机器 Schema、父子、重复/冲突和内容自洽校验。

## 12.3 Agent 与下游边界

- Agent 不创建正式分类，只返回候选分类建议；
- Agent 不负责审核结果回流，仅发布打标结果和审核所需信息；
- 只有自动通过的商品才生成商品搜索词；Agent 只发布搜索词，搜索中台负责写索引；
- 输出采用版本化 `ProductLabelResult`，包含类目 ID/名称、`taxonomy_version`、置信度、决策状态、原因码、证据、模型/Prompt 版本及可选搜索词/候选建议。

## 12.4 首期验收目标

- 二级 `Recall@20 >= 98%`；
- 一级准确率 `>= 98%`，二级整体准确率 `>= 95%`；
- 自动通过准确率 `>= 98%`；
- unknown 商品错误自动分类率 `< 2%`；
- 输出 JSON Schema 合法率 `100%`；
- 图片单点失败可降级，整单处理不得静默丢失模态。

P95 时延和单商品成本绝对阈值在模型选型与压测后另行冻结。
