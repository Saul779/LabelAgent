# LabelAgent 运行指南

本文说明如何在本地把服务跑起来，并单独触发 S1、S2、S3、S4、T1。目标是调试业务场景，不覆盖生产发布。

任务入口是消息信封，不是面向业务的同步 HTTP API。HTTP 只提供健康检查。场景 CLI 直接构造 `JobContext` 跑管线，适合改 Prompt、看单次结果；Job Worker 走完整「入站 → 场景 → 回执」链路，适合核对协议和回执。

## 1. 先选路径

| 目的 | 用哪条 | 要不要 Docker | 要不要模型密钥 |
|---|---|---|---|
| 只跑某一个场景、看 JSON 结果 | 第 5 节场景 CLI | 否 | 要 `OPENAI_API_KEY` |
| 只看 S3 文本感知，不打标 | `scripts/run_s3_perception.py` | 否 | 纯文本不需要 |
| 走回执链路，但不上 Kafka | Mock MQ Job Worker | 否 | 要。启动时会装配全部场景 |
| 用真实入站 Topic 投一条消息 | Kafka + Job Worker | 要 Kafka | 要 |
| 不调模型，只回归控制流 | 第 5.6 节 pytest | 否 | 否 |

S1 / S2 / S3 / S4 有独立 CLI。T1 没有独立 CLI，用 Mock MQ fixture、Kafka 信封，或 `tests/integration/scenarios/test_t1_pipeline.py`。

Job Worker 启动时会装配全部五个场景，包括 S4 类目索引。只想跑 S1/S2/S3/T1 时，优先用对应 CLI 或测试，避免被 S4 类目文件卡住。

## 2. 一次性准备

前置：Python 3.10、Poetry。图片 OCR 或视频还需要 `ffmpeg`、`ffprobe`，以及：

```bash
poetry run pip install -r requirements-perception.txt
```

在仓库根目录安装依赖并准备环境变量。真实密钥只放本地 `.env`，不要写回 `.env.example`。

```bash
poetry install
copy .env.example .env
```

`.env` 至少改这两项：

```text
APP_ENV=dev
OPENAI_API_KEY=你的密钥
OPENAI_BASE_URL=https://api.openai.com/v1
```

`configs/base.yaml` 的默认模型是 OpenAI 兼容接口上的 `qwen3.7-flash`（alias `primary`）和 `qwen-plus`（alias `reviewer`）。网关不是官方 OpenAI 时，只改 `OPENAI_BASE_URL`，不要改代码。配置合并顺序是 `configs/base.yaml` + `configs/{APP_ENV}.yaml` + 环境变量，环境变量优先。

下面命令默认在仓库根目录执行。Windows PowerShell 与 bash 都能跑 `poetry` / `docker`。`make` 和 `scripts/*.sh` 需要已安装 Make 或 Git Bash；没有的话用文档里的 `poetry run` 等价命令。

## 3. Docker：镜像与容器

Compose 文件在 `deploy/docker-compose.yml`。它包含两类容器：

- 依赖：Kafka（`localhost:9092`）、Kafdrop（`http://localhost:9002`）、MinIO（API `9000`，控制台 `http://localhost:9001`，账号 `minioadmin` / `minioadmin`）。
- 应用：`api`、`job-worker`。镜像由根目录 `Dockerfile` 现场构建，进程角色由 `--mode` 决定。

本地 Milvus 使用代码里的 Mock，Compose 不启动 Milvus。

### 3.1 只启动依赖

调试场景 CLI，或在宿主机跑 Job Worker 时，只拉依赖，不要同时起容器里的 `job-worker`，否则两边会抢同一个 Kafka 消费组。

```bash
docker compose -f deploy/docker-compose.yml up -d kafka minio kafdrop
docker compose -f deploy/docker-compose.yml ps
```

Kafka 对宿主机广告地址是 `localhost:9092`，容器网络内部是 `kafka:29092`。宿主机进程连 `localhost:9092`；Compose 里的应用容器已经写成 `kafka:29092`。

### 3.2 构建镜像并启动应用容器

先确认仓库根目录有 `.env`。`api` 和 `job-worker` 通过 `env_file: ../.env` 读它，同时在 Compose 里强制 `MQ_BACKEND=kafka`。

```bash
docker compose -f deploy/docker-compose.yml build api job-worker
docker compose -f deploy/docker-compose.yml up -d
```

等价的镜像标签构建：

```bash
docker build -t label-agent:local .
```

`deploy/docker-compose.prod.yml` 不构建源码，使用已发布镜像 `${IMAGE_REPO:-label-agent}:${IMAGE_TAG:-latest}`，并额外包含 `vector-worker`、`reconciliation-worker`。本地调试场景不用这个文件。

容器起来后：

```text
GET http://localhost:8000/health/live
GET http://localhost:8000/health/ready
```

`/replay` 与画像触发接口尚未装配，调用会返回未实现。它们不是场景入口。

### 3.3 停止

```bash
docker compose -f deploy/docker-compose.yml stop
```

`make compose-down` 会执行 `docker compose down -v`，连同命名卷一起删掉。只想停容器时用上面的 `stop`。

一键脚本 `bash scripts/bootstrap_dev_env.sh` 会 `poetry install`，再 `up -d` 全部服务（含 api 与 job-worker）。只要依赖时不要用它。

## 4. 本地进程

四个 mode 都是同一个入口：

```bash
poetry run python -m label_agent.main --mode api
poetry run python -m label_agent.main --mode job_worker
poetry run python -m label_agent.main --mode vector_worker
poetry run python -m label_agent.main --mode reconciliation_worker
```

有 Make 时对应 `make run-api`、`make run-job-worker`、`make run-vector-worker`、`make run-reconciliation-worker`。

| mode | 作用 | 调试场景时 |
|---|---|---|
| `api` | 运维 HTTP，端口 8000 | 只检查进程活着，不投递任务 |
| `job_worker` | 消费入站信封并执行场景 | 触发 S1–S4、T1 的全链路入口 |
| `vector_worker` | 消费 `tag.created`，写标签向量 | 依赖真实 Tag Service，且 `MQ_BACKEND` 必须是 `kafka` |
| `reconciliation_worker` | 补偿长期 PENDING 的向量 | 同上，不负责打标 |

`APP_ENV=dev` 时默认 `MQ_BACKEND=mock`：从 `MQ_MOCK_INGRESS_FIXTURE`（默认 `configs/fixtures/mq_ingress_sample.json`）读信封，处理完写到 `var/receipts/`，`MQ_MOCK_REPLAY=once` 时队列耗尽后进程退出。这份默认 fixture 里只有一条 S1 和一条 S2。

Mock 只替换消息队列，不替换模型。Job Worker 仍会调用 `.env` 里的 LLM 和 Embedding。

## 5. 单独触发场景

### 5.1 路由规则

CLI 在脚本里写死 `scene`。走 MQ 时，场景写在信封 `payload.scene`。兼容旧字段时还可以靠 `payload_type`：

| 场景 | 显式路由 | 兼容路由 | 输入要点 |
|---|---|---|---|
| S1 职业识别 | `payload.scene = "S1"` | 无，必须带 scene | 文本 / 图片 / PDF / DOCX，或多附件 |
| S2 技能证书 | `payload.scene = "S2"` | 无，必须带 scene | 同 S1 |
| S3 内容分类打标 | `payload.scene = "S3"` | `payload_type = "dynamic"` | 文本 / 图片 / 视频 |
| S4 商品打标 | `payload.scene = "S4"` | `payload_type = "product"` | `title` 与 `images` 至少有一个 |
| T1 任务详情 | `payload.scene = "T1"` | `payload_type = "task"` | `accept_mode` 为 `public` 或 `specified`；文本或图片。分支由模型判断，不能在信封里指定 |

信封外层字段固定为：`task_id`、`task_type`、`payload_type`、`payload`、`priority`（1–3）、`timestamp`（毫秒）、`callback_topic`。`callback_topic` 必须在白名单内，默认 `agent.task.callback`。`payload.event_id`、`biz_id`、`data_version` 建议带上；缺 `event_id` 时用 `task_id` 兜底。

### 5.2 S1 职业识别

```bash
poetry run python scripts/run_s1_mvp.py configs/fixtures/samples/samples_text/career_cert_sample.txt
poetry run python scripts/run_s1_mvp.py path\to\cert.png --out var\s1_result.json
poetry run python scripts/run_s1_mvp.py img1.png img2.png
poetry run python scripts/run_s1_mvp.py path\to\payload.json
```

单文件按后缀识别：`.txt` 当正文，图片当 `image_path`，`.pdf` / `.docx` / `.doc` 当文档，`.json` / `.yaml` 当完整 payload。多个材料文件会收成 `attachments`，不要把 JSON payload 和材料文件混在同一次命令里。

职业词典来自 `configs/fixtures/career_dictionary.yaml`。结果打印到终端，关注 `occupations`、`unmatched`、`audit`。

### 5.3 S2 技能证书

```bash
poetry run python scripts/run_s2_mvp.py configs/fixtures/samples/samples_text/skill_cert_sample.txt
poetry run python scripts/run_s2_mvp.py path\to\cert.png --out var\s2_result.json
```

参数与 S1 相同。词典是 `configs/fixtures/certificate_dictionary.yaml`。结果是证书 schema 4.0，看匹配证书、歧义证据和 `audit`。

### 5.4 S3 内容分类与标签

完整打标：

```bash
poetry run python scripts/run_s3_mvp.py configs/fixtures/samples/samples_text/s3_text_sample.txt --out var\s3_result.json
poetry run python scripts/run_s3_mvp.py path\to\payload.json
```

只跑感知、不召回、不打标。纯文本不调用模型：

```bash
poetry run python scripts/run_s3_perception.py configs/fixtures/samples/s3_text_sample.txt
poetry run python scripts/run_s3_perception.py path\to\poster.png --out var\s3_perception.json
poetry run python scripts/run_s3_perception.py path\to\demo.mp4
```

视频需要 ffmpeg。内容词典是 `configs/fixtures/content_dictionary.yaml`。远程图片域名默认拒绝，把域名放进 `CERTIFICATE_MEDIA_ALLOWED_DOMAINS` 或改 payload 为本地路径。

### 5.5 S4 商品打标

本地召回读取 `configs/base.yaml` 的 `scene.s4.taxonomy_path`，当前是 `docs/在场电商平台商品分类信息.xlsx`。仓库里没有这份工作簿时，S4 CLI 和 Job Worker 都会在加载类目时失败。把工作簿放到该路径，或改配置后再跑。

```bash
poetry run python scripts/run_s4_mvp.py --title "新鲜红富士苹果 5斤装"
poetry run python scripts/run_s4_mvp.py --title "无线蓝牙耳机" --image path\to\product.jpg --out var\s4_result.json
poetry run python scripts/run_s4_mvp.py path\to\payload.json --product-id p-1001
poetry run python scripts/run_s4_mvp.py payload.yaml --allow-domain img.example.com --env dev
```

payload 示例：

```json
{"product_id": "p-1", "title": "新鲜苹果", "images": ["path/to/apple.jpg"]}
```

`--title`、`--image` 会覆盖或追加到文件内容。`--image` 可重复，最多 5 张。远程 URL 必须通过 `--allow-domain` 或环境变量 `S4_MEDIA_ALLOWED_DOMAINS` 放行。首次执行会构建类目向量，耗时取决于工作簿大小和 Embedding 接口。

结果里的业务结论看 `decision`（自动通过 / 待审核 / unknown），不要只看外层是否跑完。

切到服务端类目向量时设置 `S4_CATEGORY_RETRIEVAL_BACKEND=milvus` 和 `S4_TAXONOMY_VERSION`，并保证 Milvus 代理可用。本地调试保持默认 `local`。

### 5.6 T1 任务详情

T1 没有 `scripts/run_t1_mvp.py`。真实模型用下面的单条 fixture；不调模型用 pytest。

把下面内容存成 `var/fixtures/t1_only.json`（目录可自建）。Mock fixture 可以是单个对象，也可以是数组；数组里只放一条就只会跑 T1。

```json
{
  "task_id": "task-debug-t1-001",
  "task_type": "mark_tag",
  "payload_type": "task",
  "payload": {
    "scene": "T1",
    "biz_id": "task-biz-001",
    "event_id": "evt-debug-t1-001",
    "data_version": 1,
    "accept_mode": "public",
    "title": "寻找照顾宠物的人",
    "text": "寻找一位会照顾宠物的人，需要上门。"
  },
  "priority": 2,
  "timestamp": 1720000002000,
  "callback_topic": "agent.task.callback"
}
```

PowerShell：

```powershell
$env:MQ_BACKEND = "mock"
$env:MQ_MOCK_INGRESS_FIXTURE = "var/fixtures/t1_only.json"
$env:MQ_MOCK_REPLAY = "once"
poetry run python -m label_agent.main --mode job_worker
```

bash：

```bash
MQ_BACKEND=mock \
MQ_MOCK_INGRESS_FIXTURE=var/fixtures/t1_only.json \
MQ_MOCK_REPLAY=once \
poetry run python -m label_agent.main --mode job_worker
```

`accept_mode` 只允许 `public` 或 `specified`，大小写敏感，缺了或写错会在感知之前失败，错误码 `T1_INVALID_ACCEPT_MODE`。首版只接受文本和图片，视频 / PDF 会报 `T1_INVALID_INPUT`。正文优先读 `description`、`body`、`text`、`content`、`raw_text`，也可以用 `attachments`。

模型会把任务分成 `relationship`、`skill`、`dessert` 之一再抽字段。换文案即可覆盖三条分支，例如：

- relationship：`寻找一位会照顾宠物的人`
- skill：`需要上门维修电脑`
- dessert：`可以远程，也可以到店处理`

不调用真实模型时：

```bash
poetry run pytest tests/integration/scenarios/test_t1_pipeline.py -q --no-cov
```

这条测试用脚本化 Gateway，适合改分支解析和字段校验。

### 5.7 用 Mock MQ 触发任意单个场景

做法与 T1 相同：准备只含一条信封的 JSON，设 `MQ_MOCK_INGRESS_FIXTURE` 后启动 `job_worker`。S1/S2 也可以直接用仓库自带的 `configs/fixtures/mq_ingress_sample.json`，它会按顺序跑完 S1 和 S2。

S3 文本示例把 `payload` 换成：

```json
{
  "scene": "S3",
  "biz_id": "content-001",
  "event_id": "evt-debug-s3-001",
  "data_version": 1,
  "text": "周末市集有手冲咖啡和独立乐队演出。"
}
```

同时把外层 `payload_type` 写成 `dynamic`。S4 把 `payload_type` 写成 `product`，`payload` 至少包含 `scene`、`title` 或 `images`。

回执文件在 `var/receipts/`，文件名是 `{task_id}_{timestamp}.json`。终端日志里的 `mock_ingress_acked` 带有 `outcome` 和 `published`。`once` 跑完会打印 `mock_ingress_drained` 并退出。

同一 `task_id` 再跑一遍前，先换 `task_id` / `event_id`，或清掉旧回执，避免和上一次结果混在一起。

### 5.8 用 Kafka 触发任意单个场景

1. 按第 3.1 节启动 Kafka。
2. 只启动一个消费者。容器里的 `job-worker` 和宿主机 Job Worker 不要同时使用消费组 `label-agent-consumer`。

宿主机消费者：

```powershell
$env:MQ_BACKEND = "kafka"
$env:MQ_BOOTSTRAP_SERVERS = "localhost:9092"
poetry run python -m label_agent.main --mode job_worker
```

3. 另开一个终端，把单条 JSON 打进 `agent.task.ingress`。Kafka 消息是一行一个对象，不要发 JSON 数组。

```powershell
Get-Content .\var\fixtures\t1_only.json -Raw |
  docker compose -f deploy/docker-compose.yml exec -T kafka `
    /opt/kafka/bin/kafka-console-producer.sh --bootstrap-server kafka:29092 --topic agent.task.ingress
```

4. 在 Kafdrop `http://localhost:9002` 查看入站 topic、回执 topic `agent.task.callback` 和死信 `agent.task.ingress.dlq`。消费者日志出现 `kafka_ingress_acked` 表示这条消息已执行并提交 Offset。

换场景只换 JSON 里的 `scene` 和 `payload`，Topic 与启动命令不变。

## 6. 结果怎么读

场景 CLI 把业务结果打到标准输出，`--out` 再落一份文件。Job Worker 的对外回执只有 `success` / `fail`。`NEED_REVIEW`、`PARTIAL_SUCCESS` 只要已经产出业务结果，回执仍可能是 `success`，业务状态在 `payload.decision` 或场景自己的字段里。

| 现象 | 去看 |
|---|---|
| CLI 直接报错退出 | 终端异常；多半是密钥、输入路径、S4 工作簿 |
| Mock 跑完没有文件 | `callback_topic` 是否为 `agent.task.callback`；`var/receipts` 是否可写 |
| Kafka 有入站但没执行 | 是否有且仅有一个 `job_worker`；`MQ_BOOTSTRAP_SERVERS` 是否是 `localhost:9092` |
| 消息进了 DLQ | 信封字段缺失、`priority` 不在 1–3、JSON 不是对象。日志事件 `kafka_ingress_dead_lettered` |
| 场景未命中 | `payload.scene` 是否为 `S1`/`S2`/`S3`/`S4`/`T1`。S1、S2 不能只靠 `payload_type` |
| 感知为空 | 本地文件是否存在；远程域名是否在白名单；视频是否装了 ffmpeg |
| 模型 JSON 解析失败 | `configs/base.yaml` 的 `inference.prompt_versions` 与 `src/label_agent/inference/prompts/templates/` 是否对应 |

`vector_worker` 和 `reconciliation_worker` 不产生打标回执。API 的 `/health/*` 返回 `{"status":"ok"}` 只说明进程在听端口。

## 7. 按场景回归测试

不连外部模型时，用集成测试看管线契约：

```bash
poetry run pytest tests/integration/scenarios/test_s4_pipeline.py -q --no-cov
poetry run pytest tests/integration/scenarios/test_s3_pipeline.py -q --no-cov
poetry run pytest tests/integration/scenarios/test_t1_pipeline.py -q --no-cov
poetry run pytest tests/unit tests/contract -q --no-cov
```

S1/S2 的样例与匹配逻辑在 `tests/unit` 和 `tests/integration` 中按 `s1`、`s2` 文件名检索。测试用假 Gateway，不能代替真实模型验收。
