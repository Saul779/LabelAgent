## 1. 先读结论

LabelAgent 是一个以消息队列为主入口的异步 AI 任务运行时。它不是开放式 ReAct Agent，也不是推荐系统本身；它按场景选择固定管线，把文字、图片、视频或文档转换为结构化分类、标签、职业、证书、任务字段或商品类目，再通过回执消息返回上游。

当前仓库已经具备五个已注册场景：

- S1：职业经历/职业认证识别。
- S2：技能证书识别。
- S3：动态内容分类与标签。
- S4：商品二级类目打标与搜索词生成。
- T1：任务类型判断与重点字段提取。

当前真实状态可以概括为：**五个场景的核心 MVP 管线和 Mock 测试已经形成，生产基础设施适配尚未闭环。**

本次实际验证结果：

- 121 个测试全部通过。
- 源码总覆盖率为 73%。
- 场景主管线覆盖率较高：S1 94%、S2 88%、S3 90%、S4 87%；T1 推理 84%，各分支提取器约 90%～94%。
- Ruff 在 CI/Makefile 检查范围 `src tests` 内仍有 50 项问题；把 `scripts` 也纳入时共 78 项。
- Mypy 检查仍有 23 项问题。
- `tests/e2e/` 没有真正的端到端测试。
- Kafka、真实 Tag Service、Milvus、向量 Worker、对账 Worker、API 查询/重放依赖注入仍未完成。

因此，测试全绿应理解为“当前 Mock 契约和核心逻辑可回归”，不能理解为“生产环境已经可部署”。

## 2. 项目业务边界

### 2.1 本项目负责什么

LabelAgent 负责：

1. 接收上游异步任务信封。
2. 防止重复任务产生重复副作用。
3. 按场景加载和理解输入内容。
4. 调用检索、LLM、OCR、ASR 等能力。
5. 将模型建议约束为稳定的业务 Schema。
6. 输出可审计的结构化结果。
7. 在允许的场景中经校验后创建标签。
8. 生成回执并异步返回上游。

### 2.2 本项目不负责什么

- 不负责推荐排序、用户画像存储、商品搜索索引写入或消息触达。
- 不提供面向业务的同步打标 HTTP API；HTTP 仅是运维管理面。
- 不允许模型直接创建正式分类。
- 不使用开放式自主规划循环；每个场景是可预测的固定管线。
- 不应绕过 Tag Service 直接写标签库或绕过 Milvus 代理直连向量库。

## 3. 总体架构

```text
上游业务
  │
  │ MQ TaskEnvelope
  ▼
JobWorker（Ingress Consumer）
  │ 解析、基础校验、执行场景、发布回执
  ▼
Orchestrator
  │
  ▼
ScenarioRegistry
┌──────┬──────┬──────┬──────┬──────┐
│ S1   │ S2   │ S3   │ S4   │ T1   │
└──────┴──────┴──────┴──────┴──────┘
  │
  Perception / Retrieval / LLM
  Resolution / Validation / Commit
  │
  ▼
MqPublisher → MQ Receipt Topic

旁路：VectorWorker 处理标签向量；ReconciliationWorker 做状态对账。
运维：FastAPI 提供健康检查和重放入口。
```

### 3.1 为什么使用固定场景管线

固定管线让每一步的输入、输出、失败类型和副作用位置都可追踪。LLM 只负责生成提议，代码负责候选约束、阈值、去重、安全检查和最终业务契约。这是本项目最重要的设计取舍。

### 3.2 两条运行路径

本地直接路径绕过 DB/MQ，脚本手工构造 `JobContext`，适合理解单场景和调 Prompt：

```text
本地文件/标题 → JobContext → Handler/Pipeline → JSON
```

本地 Mock 全链路直接消费 fixture 并写回执，适合理解主路径：

```text
Mock fixture → JobWorker → Orchestrator → MockPublisher → var/receipts
```

生产目标路径替换为 Kafka、真实 Tag Service、对象存储和 Milvus 代理。当前这些替换尚未全部实现。

## 4. 五个场景的当前功能

## 4.1 S1：职业识别

入口：`src/label_agent/scenarios/s1_career/handler.py`  
主管线：`src/label_agent/scenarios/s1_career/pipeline.py`

已实现流程：

```text
CertificateContentLoader
  → 职业证据和企业提取
  → 每条证据从职业内存向量索引召回 Top-5
  → LLM 在候选中选择、返回 no_match 或歧义结果
  → 按 canonical occupation_id 合并
  → 输出 occupations / unmatched / evidence / enterprises / audit
```

已实现能力：

- 支持文本、图片、PDF、DOCX 和有限 DOC 路径，而不仅是原始需求文档中的图片。
- 一份材料可提取多个职业证据，最多输出 5 个职业。
- 每条证据独立检索和匹配，避免整份简历只得到一个职业。
- 支持明确 `no_match`，不强迫从候选中选择。
- 支持按 canonical ID 合并别名职业。
- 支持企业名称提取、PII/Prompt 注入标题过滤和公开 `audit` 标记。
- 模型解析连续失败时返回空业务结果，`audit=0`。

当前缺口：

- 当前职业词典是 `configs/fixtures/career_dictionary.yaml` 内存样例，不是正式职业主数据服务。
- 需求文档对“只允许图片”与代码对“多格式输入”的口径不一致，需要产品确认。
- S1 最终结果采用精简业务契约，没有 S2 那样完整的 schema/version/model 元数据；设计文档和代码注释仍存在“schema 2.0”旧称。
- 真实 OCR、视觉模型、职业匹配准确率、多人多经历简历等尚未形成离线评测集。
- 未实现用户画像写回；这本来也应由上游业务服务负责。

## 4.2 S2：技能证书识别

入口：`src/label_agent/scenarios/s2_skill/handler.py`  
主管线：`src/label_agent/scenarios/s2_skill/pipeline.py`

已实现流程：

```text
CertificateContentLoader
  → 技能证书证据提取
  → 每条证据召回 Top-5 标准证书
  → LLM 选择 matched / ambiguous / no_match
  → 按 canonical certificate_id 合并
  → 输出 schema 4.0
```

已实现能力：

- 输入感知能力与 S1 基本一致。
- 最终只输出标准技能证书，不再混入通用技能标签。
- 输出包含证书、未匹配/歧义证据、审计标记、词典快照、Prompt/策略版本和感知降级信息。
- 非法的模型候选 ID 不会越过 Top-5 候选约束。
- 同一标准证书的多条证据会合并，重复证书 ID 被 Schema 拒绝。

当前缺口：

- 正式证书库和稳定发布流程没有接入。
- `dictionary_snapshot` 只来自本地 YAML 内存索引。
- 未形成真实证书图片、遮挡、低清晰度、多证书同图等专项验收。
- 代码注释、部分测试文件标题仍写 schema 2.0，而实际契约已是 4.0，需要统一。

## 4.3 S3：动态内容分类与标签

入口：`src/label_agent/scenarios/s3_content/handler.py`  
主管线：`src/label_agent/scenarios/s3_content/pipeline.py`

已实现流程：

```text
ContentBundleBuilder
  → 分类候选 + 标签候选并行召回
  → SemanticProposer
  → EntityResolver
  → PreValidator
  → TagCommitter
  → PostValidator
  → ContentLabelResult
```

已实现能力：

- 支持文本、图片、视频及混合输入的统一 `ContentBundle`。
- 图片可以走视觉理解；视频具备 ffmpeg 抽帧、OCR 和音轨 ASR 代码路径。
- 标签召回已实现 exact、alias、字符 n-gram/BM25 风格匹配和 RRF 融合。
- 分类从只读字典选择；一级分类低于 0.5 时回退“未分类”，二级分类可为空。
- 标签只保留置信度不低于 0.5 的前 5 个，并按置信度降序。
- `PreValidator` 在任何写入前整单校验模态完整性、EvidenceRef，以及新标签名称、领域白名单、敏感词、PII 和注入风险。
- 新标签创建入口集中在 `TagCommitter`，只负责 Tag Service 查重、幂等创建和结果组装。
- 默认 `auto_create_unmatched=false`，本地 MVP 不真正创建未命中标签。

当前缺口：

- 开发环境仍默认使用 `FixtureTagServiceClient`；生产环境通过
  `TagServiceHttpClient` 接入真实 Tag Service，需与服务端联调接口契约。
- `VectorMatcher` 已有内存实现；生产 Tag Service 搜索响应可携带
  `match_source=vector` 候选并进入 RRF 融合。
- PreValidation 尚未实现独立的 JSON Schema 校验；ID 合法性和 canonical 去重已由 `EntityResolver` 负责。
- 新标签异步向量闭环已实现：Kafka `TagCreated` → `VectorWorker` →
  Embedding → Milvus 代理 → Tag Service `READY` 回写，并由
  `ReconciliationWorker` 补偿长期 `PENDING`；上线前需确认外部端点和事件字段完全一致。
- OCR/ASR 是可选依赖，Docker 镜像没有安装 `requirements-perception.txt`，也没有安装 ffmpeg。
- 远程媒体默认空白名单；生产域名和对象存储下载适配没有完成。
- 本地 `var/s3_perception_*.json` 是旧运行产物，不能作为当前契约的回归基线。

## 4.4 S4：商品打标

入口：`src/label_agent/scenarios/s4_product/handler.py`  
主管线：`src/label_agent/scenarios/s4_product/pipeline.py`

已实现流程：

```text
标题/0~5 张图片
  → 每张图片 OCR + Vision 并行
  → 商品语义分析
  → 二级叶子类目 exact/alias/BM25/vector + RRF Top-20
  → 模型 A 分类
  → 不同 alias 的模型 B 独立复核
  → 规则决策
  → classified 时生成搜索词；unknown 时可生成候选类目建议
```

已实现能力：

- 从 Excel 工作簿导入商品类目，使用完整父子路径生成内容确定性的稳定 ID 和 taxonomy version。
- 将类目快照持久化到 `var/taxonomy/`。
- 生产可切换 `category_retrieval_backend=milvus`，复用通用 `EmbeddingProvider` 与
  `MilvusProxyClient` 从服务端类目向量库召回 Top-20；本地 xlsx 索引仅作为 MVP 回退。
- 只检索二级叶子，一级类目由父 ID 推导，避免同名二级类目串类。
- 支持仅标题、仅图片、标题加图片；图片最多 5 张。
- 支持本地路径、data URL 和白名单内 HTTP(S) 图片，统一解码为 PNG；GIF 取首帧。
- OCR 与 Vision 单路失败可以降级。
- 两模型同意同一二级类目、父子关系有效、最低置信度不低于 0.85，且未命中冲突/排除/严重降级规则时自动通过。
- 最终置信度取两个模型置信度的较小值。
- `classified`、`unknown`、`need_review` 的业务契约不变量由 Pydantic 强制校验。
- 只有自动通过才生成搜索词；unknown 可以生成类目建议，但不会创建正式类目。

当前缺口：

- 生产向量召回已完成客户端适配，但仍需与服务端联调 collection、`taxonomy_version`
  过滤及命中 metadata 契约；metadata 必须包含二级类目、父类目和规则字段。
- 本地 xlsx 仅用于 MVP；生产使用 Milvus 后容器不依赖该文件。若容器仍选择
  `category_retrieval_backend=local`，则需要额外挂载工作簿。
- Dockerfile 同样没有安装 OCR 可选依赖；图片场景可能退化为只依赖 Vision。
- 当前双模型独立性只通过不同 alias/model_name 配置约束，需要在真实模型服务上验收供应商、模型族和 Prompt 隔离。
- 缺少真实图片格式矩阵、标题图片冲突、排除词、类目边界和 259 条路径覆盖评测。

类目知识富化、向量入库以及类目版本发布/回滚由服务端类目平台负责，不属于
LabelAgent 的生产职责。

## 4.5 T1：任务详情提取

入口：`src/label_agent/scenarios/t1_task_detail/handler.py`  
推理：`src/label_agent/inference/t1_task_detail.py`

已实现流程：

```text
文本/图片感知
  → LLM 在 relationship / skill / dessert 中三选一
  → 对应 Extractor 再调用一次结构化提取
  → 生成字段和 extraction_errors
  → 映射 SUCCEEDED / PARTIAL_SUCCESS / NEED_REVIEW
```

分支行为：

- `relationship`：提取 `relation_target` 与 `relation_target_detail`。
- `skill`：提取并去重 `required_skills`，同时提取 `service_mode`。
- `dessert`：当前是“其他任务”的历史兜底编码，只提取 `service_mode`。

已实现能力：

- 强制 `accept_mode` 只能是 `public` 或 `specified`，并在感知前拒绝非法值。
- 模型输出严格禁止额外字段，解析失败会重试一次，再失败转人工复核异常。
- 对目标不明确、技能缺失、线上/线下冲突等情况返回机器可读错误码。
- 结果有歧义时映射 `NEED_REVIEW`，缺少非关键字段时映射 `PARTIAL_SUCCESS`。
- 支持显式 S1～S4/T1 scene 路由和旧 `payload_type=task` 兼容路由。

当前缺口：

- `dessert` 作为通用兜底名称容易误导，需确认是否保留协议编码并在代码中使用更清晰的内部名称。
- 任务分类需求图中的字段、异常策略和后端补充字段仍需产品最终冻结。
- 没有正式的 `run_t1_mvp.py`，新人只能通过测试或 Worker 路径调试。
- 图片输入只有 Mock 测试，缺少真实任务图片评测和端到端回执样例。

## 5. 可靠性主链路完成度

### 5.1 已完成

- `EnvelopeParser` 支持 v1 信封和 v2 扩展字段降级读取。
- `JobWorker` 直接消费 MQ，执行 Orchestrator，进程内退避，超过次数后发失败回执。

- 通用任务 Kafka IngressConsumer 和回执 Publisher 已实现手动 Offset 确认；失败时 seek 回当前消息。
- JobWorker 即入站消费者，K8s 只需 job-worker Deployment。
- K8s ConfigMap 已显式设置 `MQ_BACKEND=kafka` 和向量事件 topic/group。
- VectorWorker 和 PENDING 向量补偿已实现。
- DLQ 重放用例、脚本和 API 依赖注入未实现。
- API `/replay` 启动后会在调用时失败；只有健康检查能独立工作。
- `/health/ready` 只返回 `ok`，没有检查 MQ、Tag Service 或模型服务。

### 6.1 依赖方向的直觉

- `domain` 定义“业务对象是什么”，不应依赖外部 SDK。
- `application` 定义“一个 Job 怎么被驱动”。
- `scenarios` 定义“每个场景按什么步骤执行”。
- `perception/retrieval/inference` 提供可替换的能力。
- `resolution/validation` 将不稳定模型输出收敛为稳定业务结果。
- `infrastructure` 负责把接口接到外部系统。
- `workers/api/scripts` 只是不同进程和调试入口。

## 7. 关键数据对象

- `TaskEnvelopeV1` / `ParsedEnvelope`：MQ 任务信封及 v2 扩展。
- `JobContext`：一次 Job 内的工作记忆，不是跨会话记忆。
- `ContentBundle`：所有感知结果的统一载体，包含规整文本、图片、OCR、ASR、成功/失败模态和版本。
- `CategoryCandidate` / `TagCandidate` / `ProductCategoryCandidate`：召回候选。
- `SemanticProposal`：S3 的模型提议。
- `CertificateEvidence`：S1/S2 从材料提取出的单条证据。
- `ContentLabelResult` / `ProductLabelResult` / `TaskDetailResult`：场景最终结果。
- `Receipt`：唯一对外异步回执，外层状态只有 `success` 或 `fail`。

注意：业务上的 `unknown`、`need_review`、`PARTIAL_SUCCESS` 可以仍然对应技术处理成功的回执，具体业务状态必须看 payload。

## 10. 推荐断点和排错方法

### 10.1 场景未命中

按顺序检查：

1. `EnvelopeParser.parse()` 得到的 `v2.scene`。
2. 各 Handler 的 `can_handle()`。
3. `ScenarioRegistry.resolve()` 是否已注册。
4. 旧协议是否依赖 `payload_type` 兼容路由。

### 10.2 感知结果为空

检查：

1. `InputRouter.route()` 生成的附件类型和路径。
2. `MediaGuard` 是否拒绝远程域名、大小或私网地址。
3. `ContentBundle.failed_modalities` 和 `ctx.degraded_modalities` 是否一致。
4. OCR/ASR 可选包是否安装。
5. ffmpeg/ffprobe 是否在 PATH。
6. 图片/PDF 是否真实可解码，而不仅是扩展名正确。

### 10.3 模型输出解析失败

检查：

1. 当前 `prompt_version` 是否存在对应 YAML。
2. `PromptManager.render()` 的模板变量是否齐全。
3. Provider 是否返回纯 JSON，是否被 Markdown fence 包裹。
4. Pydantic `extra=forbid` 拒绝了哪个字段。
5. 模型 ID 是否存在于候选 Top-K 中。

不要为了“让模型通过”放宽最终业务 Schema；应先修 Prompt、解析和候选约束。

### 10.4 Job 一直不执行

检查 Kafka Consumer Group Lag、入站 Topic 是否有消息、`payload.scene` 是否可路由，以及 JobWorker 日志中的解析/执行错误。

### 10.5 有结果但没有回执

检查：

1. callback topic 是否在白名单。
2. 回执是否超过 900KB 被改成失败回执。
3. Mock Publisher 的 `receipt_dir` 是否可写。
4. 发布失败是否导致 Offset 未提交（日志 `job_retry_wait` / `回执发布失败`）。

## 11. 如何修改和新增代码

### 11.1 修改 Prompt

1. 在 `src/label_agent/inference/prompts/templates/<scene>/` 新增版本文件。
2. 不要原地覆盖已经用于结果审计的旧版本。

4. 增加解析失败、额外字段、空结果和边界样本测试。
5. 确认最终结果仍记录 Prompt 版本。

### 11.2 新增场景

1. 在 `domain/models/` 定义严格结果契约，并提供 `to_receipt_payload()`。
2. 在 `scenarios/<scene>/` 实现 Handler 和固定 Pipeline。
3. 所有模型访问经 `LlmGateway`，所有外部依赖经接口注入。
4. 在 `bootstrap/` 装配依赖。
5. 在 `ScenarioRegistry` 注册 Handler。
6. 增加 unit、integration、contract 三层测试。
7. 增加 Mock MQ 回执样例和端到端测试。
8. 不修改 Consumer/ProcessTask 的通用控制流。

### 11.3 新增标签写入逻辑

- 只能经过 `resolution/tag_committer.py`。
- 写入前必须校验领域、名称、PII、注入、敏感词、证据和候选合法性。
- 必须设计稳定幂等键。

### 11.4 新增外部系统适配

- 在 `infrastructure/` 实现接口，不要把 HTTP/Kafka SDK 代码写进 Scenario。

## 16. 常见误区

- 测试全绿不等于真实 LLM、Kafka、Tag Service 和 Milvus 已验收。
- `var/` 下旧 JSON/回执可能使用旧 Schema，不应直接复制为新契约。
- `vector_worker` / `reconciliation_worker` 骨架仍在源码中，但已不再出现在 CLI / Makefile / compose。
- API 能启动不代表重放可用。
- 配置文件里列出 Azure/vLLM alias，不代表 Provider 已实现。
- S3 注释列出的校验项不等于当前代码全部执行了这些校验。
- 不要在 Scenario、Extractor 或 Proposer 内直接写外部数据库。
- 不要把 `unknown/need_review` 简单当成技术失败；先看场景结果契约。
